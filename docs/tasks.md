## 進め方

- 1回に1タスクだけ実装する（[AGENT.md](AGENT.md)）。上から順に進める
- T01 の前に git を始める（Step 6）。「一時的に足して戻す」確認と「差分を貼る」確認は、git があることを前提にする
- 「着手前に決めること」は、実装を始める前に人が決める。決まったら、このファイルか該当する docs に書いてから実装する
- 受け入れ基準の検証は人が行い、`docs/verification/<タスクID>.md` に記録する（[ADR 0005](decisions/0005-spec-driven-process.md)）。AI は下書きまで
  - 検証ログの先頭には、次の形で状態と分担を書く。下書きの間は「状態: 下書き（日付）」にし、人が判定を終えたら「検証済み（日付）」に変える

    ```
    > 状態: 検証済み（2026-09-24）
    > - 下書き: AI（Claude Code）
    > - 判定: 人（作者）
    ```

- 「確かめ方」の列の読み方
  - 「AI：」の行は、AI が実行した出力（コマンド、ログ）を検証ログの下書きに貼る。人はそれを見て判定する。必要なら人が自分で実行し直す
  - 「人：」の行は、AI には確かめられないもの（画面の見え方、操作の手触り、ブラウザでの動作）を表す
  - AI がサンドボックスの中でウィンドウを開けるかは、T01 で最初に確かめる。開けなければ、ウィンドウを開く必要がある「AI：」の確認は、人が行う
- T05 までは、画面の文字を raylib に組み込まれたフォントで描く。AGENT.md の「フォントは JetBrains Mono」の一時的な例外で、T05 で JetBrains Mono に切り替える

### T01 ビルドの土台とウィンドウ

**目的**：C++20、警告をエラーとして扱う設定、例外なしのビルドの上で、ウィンドウが開いて固定ステップのループが回る状態を作る。以降のすべてのタスクの土台になる。

**作業**

- 最初に、AI がサンドボックスの中でウィンドウを開けるかを確かめ、結果を完了報告に書く
- `CMakeLists.txt` を作る
  - C++20
  - FetchContent で raylib `6.0` をタグで取得する
  - 自分のコードにだけ `-Wall -Wextra -Wpedantic -Werror` と `-fno-exceptions` を付ける。raylib のヘッダでは警告を出さない
  - `$<$<CONFIG:Debug,RelWithDebInfo>:DEBUG>` を定義する
- `src/main.cpp` を作る
  - 先頭に、design.md §2 の形でプラットフォームの `#if` を作る。Web の分岐も書くが、動くことは T03 で確かめる
  - 480×640 のウィンドウを開く（大きさの決め方は T05 で決めるので、ここでは 480×640 のまま）
  - `InitWindow` の後に `SetExitKey(KEY_NULL)` を呼び、Esc で終了しないようにする（design.md §2）
  - ADR 0003 の固定ステップのループを、`src/core/` に置く
  - 画面に文字を1つ描く（動いていることが分かれば何でもよい）
- `README.md` に、デスクトップ版のビルド手順を書く

**着手前に決めること**

- 書式（インデントなど）：AI が決めて完了報告に書くか、clang-format を入れるか（入れるなら先に ADR が要る）。design.md §5
  - **決定（2026-09-24）**：AI が決めて完了報告に書く。clang-format は入れない
- CMake の最低バージョン：FetchContent の `SYSTEM`（外部のヘッダの警告を消す指定）は CMake 3.25 から。候補は、3.25 に上げる（ADR 0001 を直す。手元は 4.2.1。CI のランナーの CMake は、最初に CI を作るタスク（T11）で確かめる）か、3.20 のまま別の書き方で警告を消すか
  - **決定（2026-09-24）**：3.25 に上げる。raylib 6.0 の CMakeLists.txt 自体が 3.25 を要求していた。ADR 0001 を直した
- `CMAKE_BUILD_TYPE` を指定しなかったときの扱い：指定しないと3つの構成のどれでもないビルド（`DEBUG` なし、`assert` あり）になる。候補は、既定の構成を CMakeLists.txt で決めるか、README で必ず指定させるか
  - **決定（2026-09-24）**：構成を1つだけ持つジェネレータ（Makefiles など）で指定がなければ Debug にし、そのことを設定のログに出す。README でも構成を指定する手順にする
- `src/core/` に置くファイルの名前と、公開する関数の形（C4）
  - **決定（2026-09-24）**：`src/core/fixed_step.h` と `.cpp`。`FIXED_DT` と `MAX_FRAME_TIME` を定数で持ち、クラス `FixedStep` の `[[nodiscard]] int advance(float frame_time)` が、経過時間（`MAX_FRAME_TIME` で打ち切る）を溜めて、このフレームで `update()` を回す回数を返す。`GetFrameTime()` を読んで `update(FIXED_DT)` を回数分呼ぶのは `main.cpp` の `frame()`

### T02 検査スクリプト

**目的**：AGENT.md の「検査」の表のうち、CMake のスクリプトで確かめるものを、ビルドのたびに確かめる。早く入れるほど、後のコードが最初から検査される。

**作業**

- CMake のスクリプト（`cmake -P` で動くもの）を作り、ビルドのたびに実行する
- 検査の対象は `src/` の `.h` と `.cpp`。外部のコードと生成したファイルは対象外
- スクリプトは、ビルドのたびに `src/` を自分で探して対象のファイルを集める（CMake の設定のときに作った一覧を使うと、あとから置いたファイルが見えない）
- 次の違反があれば、ファイル名と行番号を出してビルドを止める
  1. プラットフォームを判定するマクロ（`PLATFORM_WEB`、`__EMSCRIPTEN__`、`_WIN32`、`_MSC_VER`、`__MINGW32__`、`__APPLE__`、`__linux__`）が、`main.cpp` の先頭にある1つの `#if`（`#elif` と `#else` を含む）の外にある
  2. 使わない関数（ADR 0006 の表のうち、確かめ方が「スクリプト」の行）を使っている
  3. 入力・時間・乱数の関数（AGENT.md の「構造」の一覧）を、`main.cpp`、`src/core/`、`src/debug/` の外で使っている
- 500行を超えたファイルがあれば、警告だけを出す（`wc -l` と同じ数え方）

**着手前に決めること**

- スクリプトの置き場所（design.md §3 にない。`tools/` には quine_pack しかない）。候補：`cmake/`、`tools/checks/`。決めたら design.md §3 に足す
  - **決定（2026-09-24）**：`cmake/check_sources.cmake`。design.md §3 に足した
- 「`std::stoi` など、文字列を数値に変える関数」に何を含めるか。案：`std::stoi`、`stol`、`stoll`、`stoul`、`stoull`、`stof`、`stod`、`stold`。`atoi` や `strtol` のような C の関数も含めるか
  - **決定（2026-09-24）**：`stoi`、`stol`、`stoll`、`stoul`、`stoull`、`stof`、`stod`、`stold` に加え、C の `atoi`、`atol`、`atoll`、`atof`、`strtol`、`strtoll`、`strtoul`、`strtoull`、`strtof`、`strtod`、`strtold` も止める（C の関数は例外を投げないが、「数値は JSON から読む」は同じく当てはまる）
- コメントと文字列の中に出てくる名前も違反にするか（文字列の一致で判定するので、除くならその処理が要る）
  - **決定（2026-09-24）**：コメント（`//` と `/* */`）と、文字列と文字のリテラルの中身を除いてから検査する。生文字列 `R"(…)"` は扱わない
- 文字列の一致で起きる、すり抜けと誤判定への対処。次の案で判定する
  - **決定（2026-09-24）**：下の案どおりにし、さらに3つ足す。(1) 名前と `(` や `<` の間に空白があっても止める（`x.at (1)` など）(2) 文字列を数値に変える関数は `std::` がなくても止める（ADL で `stoi(s)` が通るため）(3) `#include <filesystem>` も止める
  - `.at(` と `->at(`、`.value(` と `->value(` を違反にする。`.value_or(` は違反にしない
  - `std::get<` と `std::get(` に加えて、`std::` を付けない `get<`（C++20 では ADL で `get<0>(t)` が通る）も違反にする。`get` の前が識別子の文字でないときだけ一致させる（`budget<` を止めない）。ただし nlohmann/json の `j.get<int>()` のような `.get<`、`->get<`、`.template get<`、`->template get<` は除く（ADR 0006 で、レビューで確かめることになっている）
  - `rand` は、前後が識別子の文字でないときだけ一致させる（`operand` や `random_seed` を止めない）
- 「`main.cpp` の先頭にある1つの `#if`」の「先頭」の決め方（案：`main.cpp` の中でプラットフォームのマクロを使う `#if` が1つだけで、その `#if` から対応する `#endif` までの外にマクロが出てこない）
  - **決定（2026-09-24）**：案どおり

**受け入れ基準**

| # | 基準 | 確かめ方 |
| --- | --- | --- |
| 1 | 違反のない今のコードで、ビルドが通る | AI：ビルドする |
| 2 | 上の違反 1〜3 の種類ごとに、違反を含むファイルを一時的に置くと、CMake の設定をやり直さずにビルドが止まり、ファイル名と行番号が出る。`->at(`、`get<0>(t)` のように、上で決めた形も止まる | AI：種類ごとに試して戻す。人：違反の見本と結果を検証ログで確かめる |
| 3 | 違反でないもの（`.value_or(`、`operand`、`std::get_if`、`j.get<int>()`、`j.template get<T>()`、`budget<`）は止めない | AI：一時的なファイルで試して戻す |
| 4 | 501行のファイルを置くと警告が出て、ビルドは止まらない | AI：試して戻す |

**目的**：T01 と同じ画面を、Emscripten でビルドしてブラウザで動かす（ADR 0004「雛形の段階から Web 版のビルドを通す」）。

**作業**

**着手前に決めること**

  - **決定（2026-09-24）**：最小のものを書く。`minshell.html` は外部のスクリプト（`cdn.jsdelivr.net` の FileSaver.js）と raylib の宣伝用の情報を含み、削ると最小のものとほぼ同じになるため。黒い背景、中央の `<canvas>`、ログをブラウザのコンソールに出す設定、起動時に `<canvas>` へフォーカスを移す処理だけを持つ

  - **決定（2026-09-24）**：`emrun`

### T05 画面の拡大とフォント

**目的**：ADR 0008 のとおり、480×640 の座標を拡大し、ウィンドウの実際の解像度で文字をくっきり描く。

**作業**

- 起動時にウィンドウの大きさを決める（デスクトップと Web）
- JetBrains Mono `v2.304` の Regular の TTF と `OFL.txt` を `assets/fonts/` に置き、出典とライセンスを記録する

**着手前に決めること**（ウィンドウの大きさと Web の基準は、design.md §5 で「雛形を作るとき」に決めることになっている項目）

- ウィンドウの大きさの決め方（デスクトップと Web）。候補：画面に収まる最大の大きさ、決まった大きさ。最大にする場合、縦横比を 3:4 に保つか、余白をどう扱うか
  - **決定（2026-09-24）**：画面に収まる最大の大きさにし、縦横比は 3:4 に保つ。拡大率は、使える幅 ÷ 480 と使える高さ ÷ 640 の小さいほうを、下の刻みに切り下げる。最小は 1.0（1.0 より小さいとフォントが 12px を下回り、ADR 0002 の「コードとして読める最小の大きさ」を割るため）
    - デスクトップ：使える幅はモニターの幅、使える高さはモニターの高さの 90%。raylib ではタスクバーやメニューバーを除いた大きさを取れないので、それらとタイトルバーの分として 10% を引く。`InitWindow` の前にはモニターの大きさを取れないので、ウィンドウを隠して作り（`FLAG_WINDOW_HIDDEN`）、大きさと位置を直してから表示する
    - Web：使える幅と高さは、ブラウザの表示領域（`window.innerWidth`、`window.innerHeight`）。`main.cpp` の `#if` の中で `emscripten_run_script_int` を使って読む
- 拡大率の刻み：`LoadFontEx` のフォントの大きさは `int` なので、12 × 拡大率が整数にならないと読み込めない（たとえば 1.4 倍で 16.8px）。案：拡大率を 0.25 刻みにする。ウィンドウは 120m × 160m、フォントは 3m px になり、どちらも必ず整数になる（1.5 倍なら 720×960 と 18px）
  - **決定（2026-09-24）**：案どおり 0.25 刻みにする
- Web 版でファイルを開く基準。決めたら ADR 0006 と AGENT.md を直す
  - **決定（2026-09-24）**：どちらのプラットフォームも `GetApplicationDirectory()` を基準にする。Web では `"/"` が返るので、ファイルを仮想ファイルシステムの `/` の下に `--preload-file` で入れる（`2DShooting.data` が別にできる。T11 で公開するときは一緒に置く）。`#if` は要らない。ADR 0006 と AGENT.md に書き足した
- `data/` と `assets/` の置き方。T12 のホットリロードを見越して決める。ビルドのときに実行ファイルの横へコピーすると、編集する `data/params.json` とゲームが読むファイルが別物になる。候補：シンボリックリンクにする、DEBUG のときだけソースの `data/` を読む（ADR 0006 の「実行ファイルの場所を基準に開く」の例外になるので、ADR の直しが要る）、など。Web 版は仮想ファイルシステムの上にあるので、ホットリロードはできない
  - **決定（2026-09-24）**：実行時の置き場所は `<実行ファイルの場所>/assets/` と `<実行ファイルの場所>/data/`（Web は `/assets/` と `/data/`）。`assets/` はビルドのたびに実行ファイルの横へコピーする（フォントと音はホットリロードしない）。`data/` をどう届けるか（コピー、シンボリックリンク、DEBUG のときだけソースを読む）は T12 で決める。T05 では `data/` を使わない

  - **決定（2026-09-24）**：`assets/README.md` に、素材ごとの名前、バージョン、入手先、ライセンスを一覧にする。ライセンスの本文はフォントと同じディレクトリに置く（`assets/fonts/OFL.txt`）。`assets/fonts/` ごとコピーするので、デスクトップ版にも Web 版（`.data` の中）にもライセンスが入る。ページにクレジットを出すかは、公開のタスクで決める
- **決定（2026-09-24、着手の前の確認で追加）**：
  - `src/render/text_renderer.h` と `.cpp` に、名前空間 `stg::render` の `FONT_SIZE`（12。480×640 の座標での大きさ）とクラス `TextRenderer` を置く。メンバー関数は、`[[nodiscard]] bool load(const char* font_path, float scale)`（12 × scale px で読み込み、`Camera2D` の拡大率を scale にする）、`unload()`、`begin()` と `end()`（`BeginMode2D` と `EndMode2D`。この間の座標は 480×640）、`draw_text(const char* text, Vector2 position, Color color) const`（画面のピクセルに合わせて丸めて描く）、`[[nodiscard]] Vector2 measure_text(const char* text) const`。拡大率を決める関数とプラットフォームごとの処理は `main.cpp` に置く

### T08 確保の回数を数える仕組み

**目的**：ADR 0007 のとおり、プレイ中に動的確保が起きていないことを、数えて確かめられるようにする。弾のプールより先に入れる。

**作業**

- 確保してよい場面（起動時とデータの読み込み時）以外で確保が起きたら、`assert` で止める
- 1フレームの確保回数を、T04 のデバッグ表示に出す

**着手前に決めること**

- 「いまがデータの読み込み中かどうか」の区別のしかた（ADR 0007 で、このタスクで決めることになっている）。案：読み込みの間だけ有効にする RAII のガード、フラグを立てる関数の組
  - **決定（2026-10-02）**：RAII のガード（`debug::AllocationAllowed`）にする。スコープを抜けると自動で戻るので、途中で `return` しても戻し忘れがない。入れ子にできる（深さを数える）
- 「起動時」がいつ終わるか（案：最初のフレームを始める直前）
  - **決定（2026-10-02）**：案のとおり、最初のフレームを始める直前にする。`main()` で `run_main_loop` を呼ぶ直前に、起動が終わったことを知らせる。初めの状態を「確保してよい」にするので、`main()` より前のグローバルな変数の初期化も起動時に含まれる。エラー画面のループも同じ扱いにする
- Release ビルドで、読み込み処理（T12 など、`DEBUG` ではないコード）の中のガードをどう書くか（AGENT.md の「ほかのファイルから使う型と関数の形」に当たる）
  - **決定（2026-10-02）**：ヘッダの `#ifdef DEBUG` の `#else` に、何もしない空の `AllocationAllowed` を置く。呼ぶ側は `#ifdef DEBUG` なしで書ける。AGENT.md の「開発を助けるための機能は、すべて `#ifdef DEBUG` で囲み、Release ビルドには入れない」は、この形も満たすと読む（空の型は何もせず、Release には仕組みが入らない）
- デバッグ表示に出す回数（ADR 0007 では「1フレームの確保回数」だけ。1フレームの回数だけでは、RelWithDebInfo で1回だけ起きた違反が、1フレーム（約 16ms）しか見えない）
  - **決定（2026-10-02）**：1フレームの確保回数（許される場面の確保も含めたすべて。ただし、下の OS のライブラリの確保は除く）に加えて、起動後の違反の累計を出す

    ```text
    Alloc/frame: 0
    Alloc violations: 0
    ```

- ファイル名と、ほかのファイルから使う型と関数の形（AGENT.md により人が決める）
  - **決定（2026-10-02）**：`src/debug/allocation_counter.h` と `.cpp`（`debug_overlay.h` にならい、型の名前ではなく中身の名前にする）。名前空間は `stg::debug`。`DEBUG` のときだけ、`AllocationAllowed` のほかに次の関数を宣言する。Release では空の `AllocationAllowed` だけを置き、関数は宣言しない（`main.cpp` と `debug_overlay.cpp` から `#ifdef DEBUG` の中で呼ぶ）

    class AllocationAllowed;

    void set_os_allocation_filter(bool (*is_os_allocation)());

    // 前のフレームの確保回数（許される場面も含む）

    // 起動後の違反の累計
    [[nodiscard]] int allocation_violations();

| 2 | フレームの中で一時的に `std::vector` を確保すると、Debug では `assert` で止まり、RelWithDebInfo では回数が表示される | AI：一時的に足して試し、戻す。人：表示を見る |

**わかっていること**

- rlImGui は raylib の `MemAlloc`（中身は `malloc`）で確保している（`Raylib_6_0` のソースで確かめた）。ImGui も既定では `malloc` を使う。どちらも `operator new` を通らないので、この仕組みとはぶつからない
- （実装中に分かった、2026-10-02）macOS では、実行ファイルで置き換えた `operator new` が、OS のライブラリの中の C++ のコードからの確保にも使われる。実際に、最初のフレームの `ClearBackground` の中で GPU のドライバー（`AGXMetalG13X`）が、AppKit から呼ばれた CoreText がフォントの準備で、それぞれ確保していた（RelWithDebInfo で 30 秒あまり動かして、違反が 228,611 回）
  - リンクのオプション（`-Wl,-unexported_symbol`）で置き換えを OS から見えなくする方法も試した。しかし、Debug（`-O0`）ではゲームの `std::string` の確保の大半を見逃した。macOS の libc++ では `std::string` の関数の実体が共有ライブラリの中にあり（`extern template`。無効にする設定はない）、そこから libc++ の `operator new` を呼ぶため
- **決定（2026-10-02、実装中）**：OS のライブラリの確保は、呼び出し履歴で除く。違反の判定と回数の前に、`set_os_allocation_filter` で渡された関数で判定する。macOS の関数は `main.cpp` のプラットフォームの `#if` の中に書く。呼び出し履歴（`backtrace`）を `operator new` からさかのぼり、libc++ と libc++abi を飛ばして、最初に現れたのがこの実行ファイルならゲームの確保、それ以外なら OS の確保とする。Web 版と Windows 版では判定しない（Web 版は OS のライブラリの確保が `operator new` を通らない。Windows は確かめていない）
  - RelWithDebInfo では、アラインメント指定版の `operator new` が確保の処理を末尾呼び出しにし、呼び出し履歴から `operator new` の段が消えて、CoreText の確保（1792 バイト）が違反になった。数える処理を、各 `operator new` の中で直接呼ぶ形にして直した
  - `dladdr` は、この実行ファイルでは1回 11µs ほどかかる（名前を順に探すため）。`operator new` の段を見つけるまでの段の結果を覚えておき、その先はアドレスの範囲で比べる。OS の確保1回あたりの判定は 0.2µs ほど（確認用プログラムで測った。T08 の検証ログ）

### T09 自機の移動

**目的**：入力をフレームの最初に読んで `update()` に渡し、自機を文字で描いて動かす。雛形の最後のタスクで、ガイドの第1週の到達点（「矢印キーで動く。ブラウザでも動く」）にあたる。

**作業**

- フレームの最初に入力を読み（`src/core/`）、その結果を `update()` に渡す
- 入力の型が決まったら、ADR 0003 と design.md §1 のコード例を、入力を `update()` に渡す形に直す修正案を出す（今のコード例は `update(FIXED_DT)` だけで、入力を渡していない）。人が採用してから反映し、ADR 0003 に「更新」の行を足す
- 自機を文字で描き、矢印キーか WASD で動かす。Shift を押している間は低速にする
- 自機の当たり判定を、小さな点として常に表示する（文字で描く）

**着手前に決めること**

- 入力を渡す型の形（ほかのファイルから使う型なので、AGENT.md により人が決める）。押した瞬間の扱い（design.md §5）は T19 で決める。このタスクでは押し続けている間だけを使う

        bool left = false;
        bool right = false;
        bool up = false;
        bool down = false;

    // キーボードを読む（矢印キーと WASD、左右の Shift）

    // 入力に合わせて dt 秒ぶん動かし、位置を movable_area の中に収める

- 自機の速さと開始位置（AGENT.md の「ゲームの挙動と数値」に当たる）

- 自機と当たり判定を描く文字（requirements.md §1 では画面を作るタスクで決めることになっている。このタスクでは仮の文字でよいか）
  - **決定（2026-10-02）**：仮の文字で、自機は `A`、当たり判定は `.`。`.` は `A` の中心に重ねる。`.` は文字の下の方にあるので、点の中心が当たり判定の中心に来るように、描く位置をずらす

- 受け入れ基準5で、決まった入力の並びを `update()` に与える方法（案：`src/debug/` に、入力の並びを配列で持って `update()` を回す確認用の関数を置く。一時的なコードにして確かめたら消す、でもよい）

- T01 の仮の目印（画面を横切る `@` と、四隅と中央の `+`）をどうするか（T01 で「ゲームの中身ができたら消す」としていた）

### T10 Windows 版の CI

**目的**：main に push するたびに、Windows 版を CI で MSVC でビルドし、他の PC でも起動できる配布物（Release の exe と `assets/`）を作る。完成条件のうち「Windows 版が、ダブルクリックして起動する」と「README の手順どおりに Windows 版のビルドが通る（CI で確かめてよい）」を、ここから毎回確かめられるようにする（[ADR 0004](decisions/0004-platforms.md)）。あわせて、T06 で確かめられなかった Windows の高 DPI を確かめる（[ADR 0008](decisions/0008-screen-scaling.md)）。

**作業**

- `CMakeLists.txt` の MSVC の設定

### T12 の着手前に決めたこと（T12a と T12b に共通）

  - **決定（2026-10-02）**：`params.json` の `random.seed`。キーは T13 で足す。ホットリロードで変えても、効くのは次のプレイの開始から
- 中身の確かめ方
  - **決定（2026-10-02）**：キーがない、型が違う、範囲の外（design.md の表）のどれかなら、読み込みの失敗にする。知らないキーは、失敗にせず、ログに警告を出す（キーの書き間違いは、本来のキーがないことで失敗になる）
- ホットリロードの方式（design.md §5）
  - **決定（2026-10-02）**：0.5 秒ごとに `params.json` の中身を読み（`LoadFileText`）、前に読んだ中身と違えば、読み直す（解釈する）。確かめるのはフレームの最初（`update()` の外）。デバッグ機能なので、Debug と RelWithDebInfo にだけ入れる（AGENT.md）
  - はじめは更新時刻（`GetFileModTime`）を見る方式に決めたが、`GetFileModTime` は秒の単位でしか返さないので、同じ秒の中の2回目の保存（失敗を見てすぐ直した保存、書き込みの途中に読んで失敗したあとの書き込みの完了）を見落とし、失敗のまま止まる。レビューの指摘を受けて、中身で比べる方式に変えた（2026-10-02、人が決めた）。`params.json` は小さいので、読む時間は問題にならない。`LoadFileText` は C の `calloc`（raylib の `RL_CALLOC`）で確保するので、確保の回数を数える対象（`operator new`）ではない。中身が同じなら、`operator new` の確保は起きない
  - 読み直しに失敗した中身も「前に読んだ中身」として覚え、次に中身が変わるまでは読み直さない。壊れた中身を 0.5 秒ごとに解釈し直して、失敗のログと確保をくり返さないため。デバッグ表示の失敗は出し続ける（レビューの指摘を受けて足した。人が決めた）
  - `LoadFileText` は、読めるたびに INFO のログ（`Text file loaded successfully`）を出す（raylib 6.0 の `rcore.c`）。0.5 秒ごとに読むと、中身が変わらなくても毎分約120行のログが出て、失敗の理由のログが埋もれる。そのため、0.5 秒ごとに読む間だけ `SetTraceLogLevel(LOG_ERROR)` でログの段階を上げて raylib のログを出さず、読み終わったら、ゲームのログの段階に戻す。ゲームのログの段階は定数（`LOG_INFO`）にし、起動時に `SetTraceLogLevel` で設定する（raylib 6.0 には今の段階を取る関数がないので、戻す値を定数にそろえる）。読めなかったことと読み直しの失敗は、こちらで、状態が変わったときだけ1回ログに出す（レビューの指摘を受けて直した。人が決めた）
  - `LoadFileText` が読めなかったとき（`NULL`。ファイルがない、または空）も、覚えておく状態の1つにする。読めなかったあとに読めたときは、中身が前と同じでも読み直す（解釈する）。エディタが別のファイルに書いてから名前を変えて保存するとき、その間に読んでも、次に読めたときに成功に戻るようにするため（レビューの指摘を受けて足した。人が決めた）
  - 比べるテキストと解釈するテキストは同じもの（1回の読み込み）にする。別々に読むと、2回目が書き込みの途中に当たって失敗し、1回目の正しい中身を覚えたまま失敗で止まるため（レビューの指摘を受けて足した。人が決めた）

### T15 の着手前に決めたこと（T15a と T15b に共通）

### T15a quine_pack を作る

**目的**：QUINE 範囲の切り出し、検査、マスクへの流し込み、生成物の出力を行う quine_pack を、CMake スクリプトで作る（design.md §4 の 1〜5 と、6 の生成物の出力まで）。ビルドには組み込まず、テストのサンプルで単体で確かめる。

**作業**

### T15b quine_pack をビルドに組み込む

**目的**：入力が変わったときに quine_pack を動かし、流し込んだテキストを実行ファイルに埋め込む。仮の雑魚を1体置き、デバッグ表示で埋め込まれたことを確かめる。

**作業**

- `CMakeLists.txt`：`add_custom_command` で `<build>/generated/enemy_text_data.cpp` を作る（`DEPENDS` は、`src/enemies/` を `file(GLOB_RECURSE … CONFIGURE_DEPENDS)`、`data/masks/` を `file(GLOB … CONFIGURE_DEPENDS)` で取った一覧と、`quine_pack.cmake`。quine_pack には絶対パスを渡す）。生成物と `src/enemies/` のソースを `2DShooting` に足す
- `src/enemies/enemy_text.h` と `.cpp`：`EnemyText`、`all_enemy_texts` の宣言、`find_enemy_text`
- `src/enemies/zako_dummy.h` と `.cpp`、`data/masks/zako_dummy.txt`：仮の雑魚
- `cmake/check_sources.cmake`：`src/enemies/` の外の `QUINE-BEGIN` と `QUINE-END` を違反にする。マーカーはコメントなので、コメントを取り除く前の行で、行の先頭の `// QUINE-BEGIN` と `// QUINE-END` を探す（既存の検査は、取り除いたあとのテキストのまま）。ファイルの先頭の説明も直す（レビューの指摘を受けて足した。人が決めた）
- `src/debug/enemy_text_list.h` と `.cpp`：埋め込んだ敵の一覧。`debug_overlay.cpp` から呼ぶ
