# ADR 0002: 敵の体に表示するテキスト

- 日付: 2026-09-22
- 状態: 採用
- 更新: 2026-09-23（QUINE 範囲の制約としてルール5の追記とルール7を加え、フォントの大きさの意味を追記）
- 更新: 2026-09-23（文書の見直しを受けて、マーカーの行の扱い、敵 ID、マスクの条件、空白のまとめ方、数値と大文字の名前の判定のしかた、空白が入ったマスの当たり判定を決めた。フォントのバージョンと入手先の参照先を追記）

## 背景

このゲームの核は Quine の要素で、敵の体を「その敵自身を定義しているテキスト」で描く（[requirements.md](../requirements.md)）。

最初は、敵の動きを実装した C++ ソースをそのまま並べて表示する案だった。しかしプレビューで確かめると、ただのコードの塊にしか見えず、敵だと分からなかった。
そこで IOCCC の作品のように、**ソースコードの文字で敵の絵を描く**方針に変えた。

絵を描く方法の候補は次の2つだった。

- A. 敵の形（マスク）を別に用意し、ビルド時にコードの文字を詰める
- B. ソースファイル自体を絵の形に書き、そのままコンパイルが通るようにする（IOCCC 流）

## 決定

**A. 敵の形にコードを自動で流し込む。** 次のルールで扱う。

### ルール1: 流し込むコードの範囲をマーカーで区切る

`// QUINE-BEGIN <敵ID>` の行と `// QUINE-END` の行にはさまれた行を、その敵に流し込むコードとする。マーカーの行そのものは含めない。
範囲は1つの敵につき1つとし、その中に関数を複数書いてよい。
リポジトリ上のコードは普通の読みやすい形で書く。

敵 ID は英小文字・数字・`_` で書く。`boss_` で始まる ID の敵をボス、それ以外を雑魚とする（ルール6の上限の区別に使う）。

同じ敵 ID の範囲が2つあるとき、または範囲とマスク（ルール2）のどちらかしかない敵があるときは、ビルドエラーにする。

### ルール2: 敵の形はマスクファイルで定義する

敵ごとにテキストのマスクファイル（`data/masks/<敵ID>.txt`）を用意する。使う文字は次の3つ。

| 文字 | 意味 |
| --- | --- |
| `#` | コードの文字を詰めるマス |
| `$` | 弱点。`$` をそのまま表示する |
| `.` | 空白 |

文字は縦長なので、横2文字で正方形の1ドットに見える。マスクを描くときの目安にする。

マスクは次の条件を満たすものとし、満たさなければビルドエラーにする。

- 使う文字は `#`、`$`、`.` だけ（行末の CR は無視する）
- すべての行が同じ長さ
- `#` が1つ以上ある
- 列数と行数がルール6の上限を超えない

### ルール3: 流し込み方

- 流し込む前に、コードの中で空白・タブ・改行（CR と LF）が1つ以上続くところを、空白1つに置き換える。範囲の最初と最後の空白は取り除く（空白をすべて消したり、改行をそのまま消したりすると、`float dt` が `floatdt` に、行をまたぐ `else` と `foo();` が `elsefoo();` になり、コードとして読めなくなるため）
- コードの文字を、マスクの `#` に左上から右へ、上の行から順に1文字ずつ詰める
- コードがマスの数より短いときは、先頭に戻って繰り返す。つなぎ目には空白を1つ入れる
- コードがマスの数より長いときは、入りきらない分を切り捨てる

### ルール4: 弱点はマスクの `$` で決める

弱点の位置は、形と一緒にマスクの中で設計する。コード側には何も書かない。
`$` は別の色で描き、狙う場所だとプレイヤーに分かるようにする。

### ルール5: 難易度はテキストから切り離す

HP、移動速度、弾の速度などの調整値は JSON で定義する。コードの文字数やマスクの大きさからは決めない。

QUINE 範囲に書いてよい数値は 0、1、2、0.5 だけとする。大文字の名前（定数とマクロ）は、raylib の `PI`、`DEG2RAD`、`RAD2DEG` だけとする。範囲の外で定数を作って、数値を持ち込めないようにするため。quine_pack は次の定義で判定する。

| 対象 | 定義 | 例 |
| --- | --- | --- |
| 数値 | 数値リテラルのトークン。10進数で、値が 0、1、2、0.5 のものだけを認める。小数点と接尾辞 `f` は付けてよい。識別子の中の数字（`Vector2`、`atan2f`）は数えない | 可：`0`、`2.0f`、`0.5f`、`.5f`　不可：`3`、`0.25`、`2u`、`0x2`、`5e-1`、`1'0` |
| 大文字の名前 | 英大文字・数字・`_` だけでできた識別子。`Vector2` や `DrawText` のように小文字を含む名前は対象外 | 可：`PI`、`DEG2RAD`、`RAD2DEG`　不可：`RED`、`FIXED_DT` |
| 文字列と文字のリテラル | 書かない | 不可：`"abc"`、`'a'` |

QUINE 範囲から呼ぶ範囲外の関数と変数にも、難易度の数値を書かない。JSON から読んだ値を渡す。これは quine_pack では検査できないので、レビューで確かめる。

### ルール6: 敵の大きさに上限を設ける

マスクの列数と行数に上限を設け、超えたらビルドエラーにする。雑魚とボスは敵 ID で区別する（ルール1）。

| 種類 | 上限 | 12px での大きさ |
| --- | --- | --- |
| 雑魚 | 24列 × 10行 | 約173 × 140px |
| ボス | 60列 × 24行 | 約432 × 336px |

値は仮。プレイテストで見直す。

### ルール7: QUINE 範囲は ASCII だけで書き、コメントを書かない

画面には ASCII の文字しか表示しないので、QUINE 範囲にも ASCII 以外の文字を書かない。コメントも書かない。説明は `QUINE-BEGIN` の上に書く。

quine_pack は、ルール5の数値・大文字の名前・文字列と文字のリテラル、コメント、ASCII 以外の文字と、ルール1の範囲とマスクの対応、ルール2のマスクの条件を検査し、違反があればビルドエラーにする。

### フォント

等幅フォント **JetBrains Mono**（SIL Open Font License 1.1）を同梱し、480×640 の座標で **12px** の大きさで描く。実際の描画では、拡大率に合わせた大きさのフォントを使う（[ADR 0008](0008-screen-scaling.md)）。この ADR の px は、すべて 480×640 の座標での大きさを表す。
1文字は約 7.2 × 14px で、画面全体に 66列 × 45行が入る。コードとして読める最小の大きさとして選んだ。
配布物にはライセンス文を含める。バージョンと入手先は [ADR 0001](0001-tech-stack.md) の表に書く。

## 理由

- 敵の形がシルエットとして見えるので、敵だと一目で分かる。近くで見るとコードでできていると気づく、という2段階の見え方になる
- 形がマスクで決まるので、コードを直しても敵の形・弱点・当たり判定が変わらない。実装を AI に任せ、コードが頻繁に書き換わる開発の進め方と両立する
- B は表示されたものがそのまま動くソースになる点で本物らしいが、1文字変えると形が崩れる。AI に実装を任せられず、期限にも合わない
- 弱点は見た目の設計の一部なので、コードではなくマスクで決める方が自然
- コードがマスより長いときに切り捨てるのは、形を優先するため。コードの長さのせいで敵の形を変えることはしない
- QUINE 範囲の数値の基準を機械的に判定できる形にしたのは、「難易度の数値」かどうかを人や AI の判断に任せると、検査できないため。0 と 1 に加えて 2 と 0.5 を認めるのは、「真ん中にそろえる」「半分にする」といったよくある計算を書けるようにするため
- 数値の書き方を10進数と接尾辞 `f` に絞るのは、判定を単純にし、画面に出たときにも読みやすくするため。文字列と文字のリテラルを書かないのは、敵の挙動には要らず、中の数字を検査するかどうかを決めずに済むため
- QUINE 範囲にコメントを書かないのは、流し込むときに改行を消して1行につなげると、`//` のあとに続くコードまでコメントに見えてしまうため。「コメントは日本語で書く」原則と「表示は ASCII だけ」がぶつからないようにする意味もある。マーカーの行を範囲に含めないのも同じ理由による
- 雑魚とボスを敵 ID の接頭辞で区別するのは、マスクの置き場所を変えず、マスクの中身を絵だけにしておけるため
- `#` のマスは、空白が入っても当たり判定を持たせる。見えないのに当たるマスができるが、コードを直しても当たり判定が変わらないこと（上の2つ目）を優先する

## 検討して見送ったもの

| 候補 | 見送った理由 |
| --- | --- |
| コードをそのまま並べて表示する | 敵だと分からない |
| B. 手で整形する（IOCCC 流） | AI に実装を任せられない。コードを直すたびに形を作り直すことになる |
| 弱点をコードのコメント（`/*$*/`）で指定する | 流し込むと弱点の位置が文字数しだいで動き、狙って設計できない |
| コードが長すぎたらビルドエラーにする | 形より先にコードの長さの都合が出てきてしまう |
| QUINE 範囲の数値を 0 と 1 だけにする | 「真ん中にそろえる」「半分にする」計算が書けず、そのためだけに JSON の項目が増える |
| 難易度の数値かどうかを AI がその都度判断する | 機械的に検査できない |
| QUINE 範囲の中で英語のコメントを認める | 1行につなげると、コメントとコードの境目が分からなくなる。「コメントは日本語で書く」原則に例外ができる |
| マーカーの行も範囲に含める | マーカーはコメントなので、ルール7に反する。1行につなげると、後ろのコードまでコメントに見える |
| 数値は値だけで判定し、書き方を問わない（`2u`、`0x2`、`5e-1` も認める） | 判定が複雑になり、画面に出たときにも読みにくい |
| 雑魚とボスをディレクトリで分ける、またはマスクの1行目に書く | ディレクトリで分けるとマスクの置き場所が変わる。1行目に書くと、マスクが絵だけでなくなる |
| 空白が入ったマスには当たり判定を持たせない | コードを直すたびに当たり判定が変わる |

## 影響と注意点

- ビルド時に、マーカーで囲んだコードの切り出し、ルール1・2・5・7の検査、マスクへの流し込みを行う仕組みが要る
- コードを切り捨てた場合、表示されない部分が出る。これは許容する
- 当たり判定は、マスクの `#` と `$` のマス1つずつに持たせる。`#` のマスに空白が入っても、当たり判定は持たせる
- QUINE 範囲から呼ぶ範囲外の関数と変数に難易度の数値がないかは、quine_pack では検査できない。レビューで確かめる
