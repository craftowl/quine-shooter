# ADR 0006: エラー処理の方針

- 日付: 2026-09-23
- 状態: 採用
- 更新: 2026-09-23（コンパイラが未決であることの参照先を直した。使わない関数の表に確かめ方の列を足し、`std::get` と `std::filesystem` を丸ごと使わないことにした）
- 更新: 2026-09-24（§6 に、Web 版でファイルを開く基準を足した。T05 で人が決めた）

## 背景

AGENT.md には「例外は使わない（失敗は戻り値で返す）」とだけ書いていた。見直したところ、次の点が決まっていなかった。

- 例外をビルドの設定でも無効にするのか、自分で `throw` を書かないだけなのか
- どの失敗を戻り値で返すのか
- 例外を投げる標準ライブラリの関数を使ってよいのか
- 戻り値をどの形にするのか
- 起動時にファイルが読めなかったら、どうするのか

また、nlohmann/json の `JSON_NOEXCEPTION` は、例外を `std::abort()` に置き換えるだけだった。書式の壊れた JSON や型の違いがあると、ゲームがその場で終了する。ホットリロード中に `params.json` を1文字書き間違えただけで、ゲームが落ちることになる。

## 決定

### 1. すべてのプラットフォームで、例外を無効にしてビルドする

clang・gcc・emcc では `-fno-exceptions` を付け、MSVC にも同じ意味の設定を入れる。`throw` や `try` を書くとコンパイルエラーになる。

### 2. 失敗を2種類に分ける

| 種類 | 例 | 扱い |
| --- | --- | --- |
| 起こりうる失敗 | ファイルがない、JSON の書き間違い | 戻り値で返す |
| バグ（起こってはいけない状態） | 添字が範囲外 | `assert` で止める（Debug ビルドでだけ働く） |

### 3. 例外を投げる標準ライブラリの関数は使わない

| 使わない | 代わりの書き方 | 確かめ方 |
| --- | --- | --- |
| `.at()` | `assert` で範囲を確かめてから `[]` | スクリプト |
| `.value()`（`std::optional` と nlohmann/json） | `has_value()` を確かめてから `*`（値がないことがありえないなら `assert` で確かめる）。JSON は §5 のとおりに読む | スクリプト |
| `std::get`（`std::variant`、`std::tuple`、`std::pair` のどれにも使わない） | variant は `std::get_if` か `std::visit`。tuple と pair は構造化束縛で受ける | スクリプト |
| `std::stoi` など、文字列を数値に変える関数 | 使わない（数値は JSON から読む） | スクリプト |
| `std::filesystem` | 使わない。ファイルの操作は raylib の関数（`FileExists`、`GetFileModTime` など）を使う。使う前に `raylib.h` で確かめる | スクリプト |
| nlohmann/json の、型を確かめない `get<T>()` | §5 のとおり、型を確かめてから取り出す | レビュー |

- スクリプトは文字列の一致で判定する。区別できるように、自作のメンバー関数に `at` と `value` という名前を付けない
- 表にない関数でも、例外を投げる条件（`substr` に範囲外の位置を渡すなど）はバグとして扱い、呼ぶ前に `assert` で確かめる

メモリ不足（`std::bad_alloc`）は対象外で、強制終了してよい。

### 4. 戻り値の形

- 値を返す関数は `std::optional<T>`、値を返さない関数は `bool` を返す
- 失敗を返す関数には `[[nodiscard]]` を付ける
- 失敗の詳細（ファイル名、キー名、理由）は、失敗した場所で raylib の `TraceLog` に出す。ログは、デスクトップでは端末に、Web ではブラウザのコンソールに出る

### 5. JSON の読み方

- `JSON_NOEXCEPTION` を定義してビルドする
- `json::parse(text, nullptr, false)` で読み、`is_discarded()` を確かめる
- 値は `contains()` や `is_number()` などで型を確かめてから取り出す。`at()`、`value()`、型を確かめない `get<T>()` は使わない
- 再読み込みに失敗したら、前の値を使い続ける

### 6. 起動時にファイルが読めなかったとき

| ファイル | 読めなかったとき |
| --- | --- |
| フォント、`params.json`、ウェーブ定義 | ゲームを始めずにエラー画面を出す。どのファイルがなぜ読めなかったかを英語で表示し、ウィンドウを閉じるまで出し続ける。フォント自体が読めないこともあるので、raylib に組み込まれたフォントで描く |
| 音 | 音を鳴らさずに続ける |

マスクはビルド時に実行ファイルへ埋め込むので、実行中に読めなくなることはない。

ファイルは作業ディレクトリを基準にせず、実行ファイルの場所を基準に開く。起動のしかたによって、作業ディレクトリが変わるため。

Web 版には実行ファイルの場所がないので、Emscripten の仮想ファイルシステムの `/` を実行ファイルの場所とみなす。どちらのプラットフォームでも、raylib の `GetApplicationDirectory()` を基準にする（Web では `"/"` を返す）。Web 版のファイルは、ビルドのときに仮想ファイルシステムの `/` の下へ入れる。

## 理由

- 配布の主力である Web 版（Emscripten）は、既定では例外を捕まえられず、`throw` した時点で強制終了する。デスクトップ版でも例外を無効にすれば、同じコードの振る舞いがそろう。ルールをコンパイラが守らせてくれる点もよい
- 戻り値は、実行中に本当に起こりうる失敗だけに使う。バグまで戻り値で返すと呼び出し側の確認が増え、かえってバグが見えにくくなる。`assert` なら原因の場所ですぐに止まり、Release ビルドでは消えるので、弾を大量に回すループにも負担が残らない
- 使わない関数を一覧にしておけば、ほとんどを文字列の一致で検査できる。一覧がなければ、どの関数が例外を投げるかを、書く人（AI を含む）が正しく覚えているかどうかに頼ることになる
- `std::get` と `std::filesystem` を丸ごと使わないのは、「variant に使ったか」「`error_code` を渡したか」を文字列では区別できないため。丸ごと使わなければ、スクリプトで検査できる。tuple と pair は構造化束縛で受けられ、ファイルの操作は raylib の関数で足りる見込み。型を確かめたかどうかは文字列では分からないので、`get<T>()` だけはレビューで確かめる
- `std::optional<T>` と `bool` は標準の型なので、自作の型を設計・保守しなくてよい。「失敗したら前の値を使い続ける」も、`if (auto p = load_params(path)) params = *p;` のように自然に書ける。失敗の理由によって呼び出し側の処理を変える場面はこのゲームでは見当たらないので、理由はログで足りる
- 起動時の失敗でエラー画面を出すのは、ダブルクリックで起動した人にも何が起きたのかが分かるようにするため。ログを出して終了するだけでは、「ウィンドウが一瞬出て消えた」ようにしか見えない。音はなくてもゲームを遊べるので、音のために起動を止めない

## 検討して見送ったもの

| 候補 | 見送った理由 |
| --- | --- |
| ビルドの設定は変えず、`throw` を書かないルールだけにする | デスクトップ版と Web 版で、例外の振る舞いが変わる |
| バグもリリースビルドで止める（常に働くチェック関数を作る） | 弾を大量に回すループに、リリースビルドでもチェックが残る |
| すべての失敗を戻り値で返す | 呼び出し側の確認が増え、バグが見えにくくなる |
| `std::filesystem` を、`error_code` を受け取る版で使い続ける | `error_code` を渡したかどうかを文字列で判定できず、レビューに頼ることになる |
| 例外を投げる関数を禁止しない | 起こりうる失敗でもゲームが落ちる。たとえばホットリロード中に、エディタの保存の一瞬だけファイルがなくなると、`std::filesystem::last_write_time` がゲームを強制終了させる |
| どの関数も `bool` を返し、値は出力用の引数で受け取る | 値を返すときは、`std::optional` のほうが「成功したときだけ値を使う」形を自然に書ける |
| 失敗の理由を列挙型で返す、または `std::expected` のような型を自作する | 理由によって処理を変える場面がなく、型を増やす手間に見合わない（C++20 には `std::expected` がない） |
| 読めなかったら、コードに持たせた既定値で続ける | 同じ数値がコードと JSON の2か所に存在することになり、いずれ食い違う |
| 読めなかったら、ログを出してすぐに終了する | ダブルクリックした人には、何が起きたのか分からない |

## 影響と注意点

- MSVC で例外を無効にする設定には少し手間がかかるので、Windows の CI でビルドが通ることを確かめる。Windows 版を MSVC と MinGW のどちらでビルドするかは、まだ決めていない（[design.md](../design.md) の「未決の設計」）
- `[[nodiscard]]` は警告を出すだけなので、警告をエラーとして扱う設定（AGENT.md）と組み合わせて、はじめて確認漏れを止められる
- 使わない関数の一覧のうち、確かめ方が「スクリプト」の行は、CMake のスクリプトでビルドのたびに検査する。「レビュー」の行はレビューで確かめる（AGENT.md の「検査」）
- raylib のファイルの関数で足りない操作が出てきたら、この ADR を見直す
