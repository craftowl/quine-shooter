# ADR 0005: 仕様駆動開発の進め方

- 日付: 2026-09-22
- 状態: 採用
- 更新: 2026-09-23（検証での AI の役割と、ADR の下書きを追記）
- 更新: 2026-09-23（「タスク」を手順3で分けた単位だけに使うよう、言い方を直した）

## 決定

専用ツール（GitHub Spec Kit、cc-sdd、Kiro など）は入れない。`docs/` のファイルと Claude Code で回す。

| 役割 | 担当 |
| --- | --- |
| 仕様・設計・判断（requirements、design、ADR） | 人。ADR は AI が下書きを出してよい |
| タスク分解（tasks） | 人が決め、AI が下書きを出してよい |
| 実装 | AI |
| 検証（受け入れ基準の確認） | 人。結果を検証ログに残す。AI はセルフチェックの報告と、検証ログの下書きまで |

機能ごとに、次の順に進める。

1. 仕様化: requirements.md に WHAT と WHY を書く
2. 設計: design.md に構造と選んだ理由を書く。大きな判断は ADR にする
3. タスク分解: tasks.md に、受け入れ基準つきの独立したタスクとして書く
4. 実装: タスク単位で AI に書かせる
5. 検証: AI がセルフチェックの結果（確かめたこと、確かめられなかったこと）を報告する。人が受け入れ基準を確認し、`docs/verification/` に記録する（AI は下書きまで）。仕様とのズレは仕様側に戻す

## 理由

- `docs/` の構成（requirements、design、tasks、ADR）はすでにできている。ツールを入れると、その流儀に合わせる手間が増える
- 「仕様駆動の型を自分で組み立てて運用した」と説明できる
- 見せたいのは AI を使ったことではなく、AI の出力を仕様に照らして検証した過程であり、それはツールがなくても残せる
- 検証を人が行うのは、AI が自分の出力を検証して記録すると自己採点になり、「AI の出力を人が検証した記録」という見せたいものの価値が下がるため。また、操作の手触り、音、ブラウザや Windows での動作は、AI には確かめられない

## 検討して見送ったもの

| 候補 | 見送った理由 |
| --- | --- |
| GitHub Spec Kit | ディレクトリ構成とコマンドの流儀に合わせ直す手間がかかる |
| cc-sdd | 日本語で要件・設計を生成できるが、すでに人が書いた docs と二重管理になる |
| Kiro | IDE ごと乗り換える必要がある |
