# ADR 0007: 動的確保の範囲と確かめ方

- 日付: 2026-09-23
- 状態: 採用
- 更新: 2026-10-02（確かめ方に、読み込み中の区別のしかた、起動時の終わり、違反の累計の表示を足した。T08 で人が決めた）
- 更新: 2026-10-02（macOS では OS のライブラリの確保も置き換えた `operator new` を通ることが分かったので、確かめ方に、その確保を呼び出し履歴で除くことを足し、理由と影響を直した。T08 の実装中に人が決めた）
- 更新: 2026-10-03（ホットリロードのために中身を確かめる読み込みも、データの読み込みに含めることを足した。T12b で人が決めた）

## 背景

AGENT.md には「ゲームループ中の動的確保は禁止。弾や敵はプールを使う」と書いていた。見直したところ、次の点が曖昧だった。

- シーン遷移のときの確保も禁止に含むのか
- デバッグ用のコードも禁止に含むのか
- Dear ImGui は内部でフレーム中にメモリを確保することがあり、こちらでは止められない

また、コードを読むだけでは、`std::string` や `std::vector` による確保を見落としていないとは保証できない。

## 決定

### 確保してよい場面

- 動的確保をしてよいのは、起動時とデータの読み込み時（ホットリロードを含む）だけとする
  - ホットリロードのために、ファイルの中身が変わったかを確かめる読み込み（0.5 秒ごとに `params.json` を `LoadFileText` で読む。raylib が C の `calloc` で確保する）も、データの読み込みに含める。ホットリロードはデバッグ機能なので、Release には入らない（2026-10-03、T12b。人が決めた）
- シーン遷移でも、デバッグ用のコードでも確保しない。弾や敵はプールを使い、シーンは先に用意しておく
- ImGui の内部で起きる確保は対象外とする

### 確かめ方

- デバッグ機能のあるビルド（Debug と RelWithDebInfo）では、グローバルな `operator new` を置き換えて、確保の回数を数える
- 起動時とデータの読み込み中以外に確保が起きたら、その場で `assert` で止める。止まった場所の呼び出し履歴を見れば、どのコードが確保したのかが分かる。`assert` が働くのは Debug ビルドだけなので、RelWithDebInfo では数えるだけになる
- 1フレームの確保回数を、デバッグ表示に出す
- 読み込み中かどうかは、RAII のガード（`debug::AllocationAllowed`）で区別する。ガードがあるスコープの中では確保してよい。入れ子にできる。Release では何もしない空の型になる
- 起動時は、最初のフレームを始める直前に終わる。`main()` より前のグローバルな変数の初期化も起動時に含まれる
- デバッグ表示には、1フレームの確保回数に加えて、起動後の違反の累計を出す。RelWithDebInfo では `assert` が働かないので、1回だけの違反が1フレームで消えて見逃されないようにする
- 起動の後は、OS のライブラリ（GPU のドライバー、CoreText など）からの確保を、違反にも回数にも入れない。macOS では、置き換えた `operator new` が OS のライブラリの中の C++ のコードにも使われるため。呼び出し履歴を `operator new` からさかのぼり、libc++ を飛ばして、最初に現れたのがゲームの実行ファイルかどうかで判定する。判定は `main.cpp` のプラットフォームの `#if` の中に書き、関数として渡す（[ADR 0004](0004-platforms.md)）

## 理由

- プレイ中に確保しないのは、1フレームのコストを一定にするため。確保にかかる時間はフレームごとに読めず、メモリが散らばると更新ループのキャッシュ効率も落ちる
- 「確保してよいのは、起動時とデータの読み込み時だけ」は、いちばん単純で検査しやすいルールになる。ポートフォリオでも「起動したあとは、データの読み込み以外で一度も確保しない」と言い切れる
- design.md にあるシーン管理の候補（`std::variant`、列挙型と switch、仮想関数）は、どれもシーンを先に用意しておけば、確保せずに作れる
- デバッグ表示は `ImGui::Text` や `TextFormat` で書けるので、確保が必要になる場面はほとんどない
- 原則を破るのはバグなので、「バグは `assert` で止める」（[ADR 0006](0006-error-handling.md)）にそろえる。警告だけでは「どこかで確保された」ことしか分からないが、止めれば原因の行がすぐに分かる
- 数えられるのは C++ の `new`（`std::string`、`std::vector`、`make_unique` など）による確保だけだが、うっかり書きやすいのはまさにここ。ImGui と raylib は `malloc` を使うので数えられないが、ImGui の内部は対象外にしたので、かえって都合がよい
- OS のライブラリの確保を、置き換えを OS から見えなくして除く方法（リンクのオプション）は見送った。macOS の Debug では、ゲームの `std::string` の確保の大半が libc++ の共有ライブラリの中で起き、見逃すため。呼び出し履歴で除く方法なら、`std::string` も数えられる
- 標準の C++ だけで作れるので、依存が増えない。「弾1万発でも確保回数0」をデバッグ表示で見せられれば、ポートフォリオの材料にもなる

## 検討して見送ったもの

| 候補 | 見送った理由 |
| --- | --- |
| シーン遷移での確保を認める | ルールが複雑になる。シーンを先に用意しておけば、確保しなくても作れる |
| デバッグ用のコードでの確保を認める | 確保の回数に余計な数が混ざる。確保しなくても書ける |
| 確保の回数を数えず、コードを読んで確かめる | 見落としがないことを保証できない |
| 確保が起きても止めず、ログに警告を出すだけにする | どのコードが確保したのかが分からない |

## 影響と注意点

- シーン管理（design.md の未決の項目）は、「遷移のたびに `make_unique` で作る」形にはできない
- 大きなプールやシーンは、起動時に確保するか、静的な領域に置く。スタックには置かない（大きな配列はスタックをあふれさせるおそれがある。特に Web 版は、既定のスタックが小さい）
- 確保を数える仕組みは、いまがデータの読み込み中かどうかを知る必要がある。その区別のしかたは、仕組みを作るタスク（T08）で決めた（上の「確かめ方」）。データを読み込む関数は、ガードを置き忘れると、ホットリロードのときに `assert` で止まる
- `malloc` による確保は数えられない。raylib がプレイ中に内部で確保しても、この仕組みでは分からない
- OS のライブラリの確保は、macOS では呼び出し履歴で除く。OS のライブラリがゲームのコードを呼び返して（GLFW のコールバックなど）、その中で確保したものは、ゲームの確保として数える。判定できないとき（`dladdr` が名前を返さない、32 段さかのぼってもゲームのコードにも OS のライブラリにも着かない）は、ゲームの確保とみなす。違反を見逃さない側に倒すため
- 呼び出し履歴からは、末尾呼び出しで抜けた段が消える。ゲームのコードが直接呼んだ OS の関数が、末尾呼び出しで `operator new` を呼ぶと、ゲームの確保と判定される（違反として表に出る側の誤り）。数える処理は、置き換えた各 `operator new` の中で直接呼び、`operator new` の段が消えないようにしている
- Windows で OS のライブラリの確保が `operator new` を通るかは、確かめていない（T10 の後）
