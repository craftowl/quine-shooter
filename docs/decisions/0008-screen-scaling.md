# ADR 0008: 画面の拡大の方式

- 日付: 2026-09-23
- 状態: 採用
- 更新: 2026-09-25（高 DPI の試行の結果を書き足した。試した結果、macOS と Web で高 DPI に対応すると人が決めた。T06）

## 背景

ゲーム内の座標は 480×640 に固定し、ウィンドウに表示するときに拡大する（[requirements.md](../requirements.md)）。このゲームの核は、敵の体の文字が「近くで見るとコードだと読める」ことで、フォントの 12px は、コードとして読める最小の大きさとして選んだ（[ADR 0002](0002-quine-enemy-text.md)）。

広く使われている 1080p のモニターでウィンドウを画面いっぱいまで大きくすると、拡大率は 1.5 倍前後の半端な値になる。拡大のしかたによって、文字の読みやすさが大きく変わる。

## 決定

- 座標だけを拡大し、ウィンドウの実際の解像度で描く
  - フォントは拡大率に合わせた大きさで読み込み（1.5 倍なら 18px）、raylib の `Camera2D` で拡大して描く
  - 「12px」は「480×640 の座標での大きさ」という意味にする
  - ゲームの処理（座標、当たり判定）は 480×640 のまま
- ウィンドウの大きさは起動時に決めて固定する
- 高 DPI の画面（表示スケールを上げた Windows、Retina の Mac、拡大率が 1 より大きいブラウザ）への対応は、雛形を作る段階で時間を区切って試す。raylib 6.0 で素直にできれば対応し、手間が大きければ対応しない。結果はこの ADR に書き足す
  - 2026-09-25 に試し、macOS と Web で対応した。Windows は T10 の後に確かめる（下の「高 DPI の試行の結果」）

## 理由

- どの拡大率でも、文字が実際の画面の解像度でくっきり描かれる。コンセプトの核である「コードとして読める」を守れる
- 変わるのは描き方だけで、ゲームの処理は 480×640 のまま変わらない
- ウィンドウの大きさを起動時に決めて固定すれば、フォントを読み込み直す必要がない。requirements.md でも、解像度は固定することになっている
- 高 DPI の画面では、何もしないと OS やブラウザが描画結果を引き伸ばすので、結局ぼやける。表示スケールを上げた Windows のノート PC はよくあるので、対応しないと、この方式を選んだ意味が薄れる。ただし、raylib 6.0 で高 DPI がどう扱われるかは試さないと分からず、Windows やブラウザでの見え方は人が確かめる必要がある。そのため、試してから決める。試した結果と判断を残すこと自体が、判断の記録になる

## 検討して見送ったもの

| 候補 | 見送った理由 |
| --- | --- |
| 480×640 のテクスチャに描いてから引き伸ばす | 文字も 12px で描いてから拡大するので、半端な拡大率では文字がぼやけるか、線の太さがそろわなくなる |
| 480×640 のテクスチャを整数倍でだけ拡大する | 文字はくっきりするが、1080p のモニターでは等倍（480×640）にしかならず、ウィンドウが小さい |
| 高 DPI に対応すると、試す前に決める | raylib 6.0 でどれだけ手間がかかるか分からない |
| 高 DPI に対応しないと、試す前に決める | 表示スケールを上げた Windows などで文字がぼやけ、この方式を選んだ意味が薄れる |

## 影響と注意点

- 雛形の段階で決めること
  - 起動時に、ウィンドウの大きさをどう決めるか（デスクトップと Web のそれぞれ）
  - 高 DPI の試行にかける時間の上限
- 文字がくっきり見えるかどうかは、人が画面を見て確かめる
- 高 DPI の試行の結果：下の「高 DPI の試行の結果」

## 高 DPI の試行の結果（2026-09-25、T06）

### raylib 6.0 で分かったこと

- デスクトップ（GLFW）で `FLAG_WINDOW_HIGHDPI` を付けると、描画の大きさ（`GetRenderWidth()`）がウィンドウの大きさ（`GetScreenWidth()`、macOS ではポイント）の倍率倍になる。raylib は `BeginDrawing` で、その倍率の行列（`screenScale`）を掛ける
- `BeginMode2D` は行列を初期化してから Camera2D の行列を掛けるので、`screenScale` は掛からない。Camera2D の中の座標は、実際のピクセルになる。そのため、Camera2D の拡大率に「480×640 の 1px が実際の何ピクセルか」を渡せば、`TextRenderer` の形を変えずに済んだ
- Web（`PLATFORM_WEB`）では `FLAG_WINDOW_HIGHDPI` はほぼ効かない（`SetWindowState` に渡すと「not available」と出る）。`GetWindowScaleDPI()` は、フラグに関係なく `window.devicePixelRatio` を返す
- Emscripten の GLFW は、高 DPI に対応させない（`GLFW_SCALE_TO_MONITOR` を付けない）と、canvas の CSS の大きさを書き換えない。そのため、canvas の中身の大きさと CSS の大きさを別々に決められる

### 試した方式

| プラットフォーム | 方式 |
| --- | --- |
| macOS | `FLAG_WINDOW_HIGHDPI` を付ける。モニターの大きさ（ポイント）に `GetWindowScaleDPI()` を掛けて実際のピクセルに直し、拡大率を決める。ウィンドウの大きさはポイントで渡す |
| Web | canvas の中身を「表示領域 × `devicePixelRatio`」のピクセルで作り、CSS の大きさをその 1/`devicePixelRatio` にする（`emscripten_set_element_css_size`）。raylib からは、実際のピクセルの大きさのウィンドウに見える |
| Windows | 高 DPI の設定を使わず、T05 のまま。GLFW が DPI に対応したアプリとして動くので、OS は引き伸ばさず、モニターとウィンドウの大きさはピクセルになる見込み。**確かめていない**（手元に Windows がない。T10 の後に、表示スケールを上げただれかの Windows で確かめる） |

どれも、拡大率は実際のピクセルで 0.25 刻みにし、最小は OS やブラウザの座標で 1.0 にした（高 DPI の画面で文字が小さくなりすぎないように）。

### 試した環境と結果

| 環境 | 倍率 | 拡大率、ウィンドウ、フォント | 見え方（人） |
| --- | --- | --- | --- |
| macOS、MacBook Pro（M1 Max）の Retina の画面（1512×982 ポイント） | 2.0 | 2.75 倍、660×880 ポイント（1320×1760 ピクセル）、33 px | にじまない。ImGui も正しい大きさでくっきり出る |
| macOS、外部モニター（1920×1080） | 1.0 | 1.5 倍、720×960、18 px | T05 と同じ |
| Chrome、外部モニター、拡大率 125% | 1.25 | 1.25 倍（最小）、600×800 ピクセル（480×640 CSS px）、15 px | 少し柔らかく見える。canvas の左端は実際のピクセルの境目にそろっていて（103.0000019）、表示の幅と中身の幅が同じ（600）なので、ブラウザは引き伸ばしていない。15 px と小さいためと考えられる（T05 の、倍率 1 で 15 px のときも同じ感想だった） |
| Chrome、外部モニター、拡大率 150% | 1.5 | 1.5 倍（最小）、720×960 ピクセル、18 px | くっきり見える。ImGui のウィンドウをマウスで動かせる。起動したあとにブラウザの大きさを変えても、canvas の大きさは変わらない |

### 判断

- 対応する（2026-09-25、人が決めた）。macOS と Web は、上の方式で文字がにじまないことを確かめた。直したのは `main.cpp` のウィンドウを作る処理だけで、`TextRenderer` の形は変えていない。試行は 16:40 に始め、画面での確認が終わった 17:08 の時点で約 30 分だった（上限は半日）
- Windows は T05 のままにし、T10 の後に確かめる。引き伸ばされていたら、この ADR を見直す
- 起動したあとに別の倍率のモニターへウィンドウを移したときや、ブラウザの拡大率を変えたときは、フォントを読み込み直さない（ウィンドウの大きさは起動時に決めて固定する、の範囲）
