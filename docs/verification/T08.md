## 実装中に起きたこと

### 1. 何もしないフレームで止まった：OS のライブラリの確保

- 起きたこと：normal-debug が、最初のフレームで `ERROR: ALLOC: 40 bytes …` を出して `assert` で止まった
- 原因：macOS では、実行ファイルで置き換えた `operator new` が、OS のライブラリの中の C++ のコードからの確保にも使われる。lldb の呼び出し履歴（人が実行）では、次の2つだった
  - `render()` → `ClearBackground` → `glClear` → `AppleMetalOpenGLRenderer` → GPU のドライバー（`AGXMetalG13X`）が、テクスチャのビューを作るときに確保していた
  - RelWithDebInfo で 30 秒あまり動かすと、違反が 228,611 回出た。止めた3回は、どれも CoreText がフォントの字形の準備（`TFont::InitShapingGlyphs`）で確保していた
- ADR 0007 は「数えられるのはゲームの C++ の `new` だけ」という前提だった。この前提が、macOS の OS のライブラリについては成り立たなかった

### 2. 試して見送った方法：置き換えを OS から見えなくする

- 試したこと：macOS でだけ、リンクのオプション `-Wl,-unexported_symbol` で、置き換えた `operator new` / `delete` を実行ファイルの外に出さないようにした。人がこの方法に決めて、いったん CMakeLists.txt に入れた
- 分かったこと：確認用プログラムでは、OS のライブラリ（の代わり）の確保は数えなくなった。しかし `-O0` では、ゲームの `std::string` の確保の大半を数えなくなった。macOS の libc++ では、`std::string` の関数の実体が共有ライブラリの中にあり（`extern template`。このバージョンには無効にする設定がない）、そこから libc++ の `operator new` を呼ぶため

  | 確保 | `-O0`、外に出す | `-O0`、外に出さない | `-O2`、外に出さない |
  | --- | --- | --- | --- |
  | OS のライブラリの代わり | 8 | 0 | 0 |
  | ゲームの `std::vector` | 1 | 1 | 1 |
  | ゲームの `std::string(100,'x')` | 1 | 0 | 1 |
  | ゲームの `std::string` の `+=` | 3 | 0 | 3 |

- 決めたこと：人が、呼び出し履歴で OS の確保を除く方法に決め直した。CMakeLists.txt の変更は戻した

### 3. 判定が遅かった

- 起きたこと：呼び出し履歴の段ごとに `dladdr` を呼ぶ最初の形では、OS の確保1回あたり 24〜59µs かかった（確認用プログラム）
- 原因：`dladdr` は、名前（シンボル）が 3,800 個ほどある実行ファイルでは、1回 11µs かかった（名前を順に探すため）。名前の少ないプログラムでは 0.6µs だった
- 直したこと：確保を数える仕組みの中の段（決まった数十個のアドレス）の結果を覚えておく。その先の段は、最初に1回だけ調べた、実行ファイル、libc++、libc++abi のコードのアドレスの範囲と比べる。直した後は 0.14〜0.27µs になった（上の「確認用プログラム」）

### 4. RelWithDebInfo で、OS の確保が違反になった

- 起きたこと：normal-relwithdebinfo で、`ERROR: ALLOC: 1792 bytes …` が 14 回出た。Debug では出なかった
- 原因：lldb の呼び出し履歴（人が実行）では、AppKit がメニューバーを描くときに、CoreText がアラインメント指定版の `operator new` で確保していた。RelWithDebInfo では、その `operator new` が確保の処理（`allocate_aligned`）を末尾呼び出しにしたため、呼び出し履歴から `operator new` の段が消えた。判定は `operator new` の段を見つけられず、決まりどおりゲームの確保とみなした
- 直したこと：数える処理を、置き換えた各 `operator new` の中で直接呼ぶ形にした。数えている間は、`operator new` の段が必ず残る。判定では、`operator new` に見える段が続くときは、まとめて飛ばすようにした。直した後、上の「実行の出力」のとおり、出なくなった

### 5. 確認用の版の作り方の誤り

- 起きたこと：allowed-relwithdebinfo で、ガードの中の確保が違反になった（641 回）
- 原因：確認用の版の中身が violate のままだった。機械語に、`AllocationAllowed` のコンストラクタを呼ぶ命令がなかった。ソースを書き換えた時刻と、直前のビルドでできたオブジェクトファイルの時刻が同じ秒で、make（時刻を秒単位で比べる）が `main.cpp` をコンパイルし直さなかったためと考えられる
- 直したこと：ビルドする前に、毎回 `main.cpp` のオブジェクトファイルを消した。作り直した版は、ガードを呼ぶ命令が allowed の2つにだけあることを確かめた

### 6. 最適化で確保が消える

- 確認用プログラムの1回目では、RelWithDebInfo 相当（`-O2`）の回数が、どこでも 0 だった。使われない `new` と `delete` の組を、コンパイラが確保ごと消したため（C++14 から、new 式による確保は省いてよい）
  - 実際に確保が起きていないので、数えないのは正しい。ただし、同じコードでも、Debug（`-O0`）と RelWithDebInfo で回数が変わることがある。RelWithDebInfo で 0 と表示されても、Debug で止まることはありうる
  - violate と allowed も、同じ理由で `alloc_sink` に位置を出している

### 7. 仕様になく AI が決めたこと

- `Alloc/frame` には、OS のライブラリの確保を入れない。着手前には「許される場面の確保も含めたすべて」と決めていたが、OS の確保を入れると、何もしないフレームでも 0 にならないため。人が承認した（2026-10-02）

### 8. 行数

- 見込みは約150行だったが、約455行になった
  - `allocation_counter.cpp`（232行）、`allocation_counter.h`（50行）
  - `main.cpp`：OS の確保の判定、設定の呼び出し、フレームと起動の終わりの知らせで、162行増えて 413行
  - ほかの変更：7行
- 置き換える関数が20個あることと、OS の確保の判定が加わったため。どのファイルも 500行を超えないので、分けていない
