# プロジェクト原則（AGENT.md）

> 実装を担当する AI が最初に読むファイル（プロジェクト直下の `CLAUDE.md` から読み込む）。原則と実態の食い違いに気づいたら、AI は報告して修正案を出す。コードと原則のどちらを直すかは人が決める。

## 役割分担

- 設計判断は人が行う。AI は `docs/` の仕様と ADR に従って実装する
- 仕様にない判断のうち、次のものは実装する前に質問する。推測で決めない
  - ほかのファイルから使う型と関数の形
  - JSON とマスクの形式
  - ゲームの挙動と数値
  - ファイルと依存の追加
- それ以外（関数の中の書き方など）は AI が決めてよい。決めたことは完了報告に書く
- 仕様と実装が食い違うことに気づいたら、仕様の修正案を出す。仕様を勝手に書き換えない
- 文書どうしが食い違うことに気づいたら、作業を止めて報告する
- ADR は AI が下書きし、人が採用を決める

## 作業の進め方

- 1回に1タスクだけ実装する。タスクと関係のないファイルの変更、リファクタリング、ついでの改善はしない。気づいたことは提案にとどめる
- タスクが終わったら、次の5つを報告する
  1. 変更したファイル
  2. 受け入れ基準ごとの確認方法と結果
  3. 確認できなかったこと
  4. 仕様になく AI が決めたこと
  5. 仕様とのズレ
- 受け入れ基準の検証と `docs/verification/` への記録は人が行う。AI は検証ログの下書きまで（[ADR 0005](decisions/0005-spec-driven-process.md)）
- raylib や ImGui の API は、取得したヘッダ（`raylib.h`、`imgui.h`）で、関数があることと引数を確かめてから使う。記憶で書かない
- 計測値（処理時間、弾数など）は、実際に測ったものだけを、条件（CPU、OS、ビルド構成、オブジェクト数）と一緒に書く。「ビルドが通った」「動いた」も、実際に実行してから書く

## 言語とビルド

- C++20。例外は無効にしてビルドする（clang・gcc・emcc は `-fno-exceptions`、MSVC も同じ意味の設定）
- 警告は `-Wall -Wextra -Wpedantic`（MSVC は `/W4`）で出し、エラーとして扱う（`-Werror`、`/WX`）。外部のライブラリは、ヘッダも含めて対象外にする
- ビルド構成は次の3つ（[ADR 0001](decisions/0001-tech-stack.md)）
  - Debug：開発用
  - RelWithDebInfo：計測とプレイテスト用（最適化あり、`assert` なし、デバッグ機能あり）
  - Release：配布用（デバッグ機能なし）
- 依存は ADR に記載があるものだけ。追加するときは、先に ADR を書く
  - GitHub 公式のアクション（`actions/` で始まるもの）は、ADR に書かずに使ってよい。それ以外のアクションと開発用のツールは、ADR に書いてから使う
  - バージョンは ADR 0001 の「バージョンの決め方」に従う。ライブラリ、フォント、Emscripten、アクション、開発用のツールは固定する。CMake とコンパイラは最低バージョンを書き、CI のランナーイメージは名前で指定する

## エラー処理（[ADR 0006](decisions/0006-error-handling.md)）

- 起こりうる失敗（ファイルがない、JSON の書き間違いなど）は戻り値で返す。バグ（起こってはいけない状態）は `assert` で止める
- 値を返す関数は `std::optional<T>`、値を返さない関数は `bool` を返し、`[[nodiscard]]` を付ける。失敗の詳細（ファイル名、キー名、理由）は、失敗した場所で `TraceLog` に出す
- 例外を投げる標準ライブラリの関数は、次の表のとおり使わない。メモリ不足（`std::bad_alloc`）は対象外で、強制終了してよい

| 使わない | 代わりの書き方 | 確かめ方 |
| --- | --- | --- |
| `.at()` | `assert` で範囲を確かめてから `[]` | スクリプト |
| `.value()`（`std::optional` と nlohmann/json） | `has_value()` を確かめてから `*`（値がないことがありえないなら `assert` で確かめる）。JSON は下のとおりに読む | スクリプト |
| `std::get`（`std::variant`、`std::tuple`、`std::pair` のどれにも使わない） | variant は `std::get_if` か `std::visit`。tuple と pair は構造化束縛で受ける | スクリプト |
| `std::stoi` など、文字列を数値に変える関数 | 使わない（数値は JSON から読む） | スクリプト |
| `std::filesystem` | 使わない。ファイルの操作は raylib の関数（`FileExists`、`GetFileModTime` など）を使う | スクリプト |
| nlohmann/json の、型を確かめない `get<T>()` | 型を確かめてから取り出す | レビュー |

- 自作のメンバー関数に `at` と `value` という名前を付けない（スクリプトが文字列の一致で判定するため）
- 表にない関数でも、例外を投げる条件（`substr` に範囲外の位置を渡すなど）はバグとして扱い、呼ぶ前に `assert` で確かめる

- nlohmann/json は `JSON_NOEXCEPTION` を定義してビルドし、次のとおりに読む
  - `json::parse(text, nullptr, false)` で読み、`is_discarded()` を確かめる
  - 値は `contains()` や `is_number()` などで型を確かめてから取り出す。`at()`、`value()`、型を確かめない `get<T>()` は使わない
  - 再読み込みに失敗したら、前の値を使い続ける
- 起動時にフォント、`params.json`、ウェーブ定義のどれかが読めなければ、ゲームを始めずにエラー画面を出す
  - どのファイルがなぜ読めなかったかを英語で表示し、ウィンドウを閉じるまで出し続ける
  - エラー画面は raylib に組み込まれたフォントで描く
- 音が読めなければ、音を鳴らさずに続ける
- ファイルは作業ディレクトリを基準にせず、実行ファイルの場所を基準に開く

## 命名とコメント

- 型は PascalCase、関数と変数は snake_case、定数は UPPER_SNAKE_CASE
- 列挙型は `enum class` にし、列挙子は PascalCase で書く（例：`SceneId::Title`）
- private メンバーにだけ、末尾に `_` を付ける（例：`count_`）
- raylib のマクロ（`PI`、`RED` など）と同じ名前を付けない
- すべてのコードを名前空間 `stg` に入れる。`main()` だけは外に置く
- ファイル名は、そのファイルの中心となる型の名前を snake_case にしたもの（例：`bullet_pool.h`、`bullet_pool.cpp`）。ヘッダの拡張子は `.h`、インクルードガードは `#pragma once`
- コメントは日本語で書く。ただし、QUINE 範囲の中には書かない

## 構造

- 更新と描画を混ぜない。`update()` の中で `Draw*` を呼ばない
- `update()` に渡す時間は常に固定の `FIXED_DT`（[ADR 0003](decisions/0003-game-loop.md)）
- `update()` の結果が入力だけで決まるようにする。ADR 0003 の「同じ入力なら同じ結果になる」は、これが前提になっている
  - `update()` の中で `GetFrameTime()`、`GetTime()`、`GetRandomValue()`、`rand()`、`IsKey*()` を呼ばない
  - これらの関数を呼んでよいのは、`main.cpp`、`src/core/`、`src/debug/` だけ
  - 入力はフレームの最初に読んで渡す
  - 乱数は自前の生成器を使い、シードはプレイのたびに同じ値にする（毎回同じ弾幕になり、覚えて攻略でき、検証でも同じ場面を再現できるため）。値の置き場所は、調整値の JSON の形を決めるときに決める
- プラットフォームで分ける `#if` は、`main.cpp` の先頭にある1つの `#if` の中だけに書く（[ADR 0004](decisions/0004-platforms.md)）。`#elif` と `#else` は同じ `#if` の一部に数える
  - 対象のマクロは `PLATFORM_WEB`、`__EMSCRIPTEN__`、`_WIN32`、`_MSC_VER`、`__MINGW32__`、`__APPLE__`、`__linux__`
  - CMakeLists.txt の中の分岐は対象外
  - `main.cpp` の外でプラットフォームの違いが必要になったら、`main.cpp` の中でその違いを値（「終了できるか」など）に変えてから渡す
- 書く行数の見込みが500行を超えるタスクでは、実装する前に分割案を出して確認する
- 1ファイルの行数は `wc -l` で数える。生成したファイルと外部のコードは数えない

## メモリ（[ADR 0007](decisions/0007-dynamic-allocation.md)）

- 動的確保をしてよいのは、起動時とデータの読み込み時（ホットリロードを含む）だけ
  - シーン遷移でも、デバッグ用のコードでも確保しない。弾や敵はプールを使い、シーンは先に用意しておく
  - ImGui の内部で起きる確保は対象外
- デバッグ機能のあるビルドでは、`operator new` を置き換えて確保の回数を数える。許されない場面で確保したら `assert` で止め、1フレームの確保回数をデバッグ表示に出す

## デバッグ機能

- `DEBUG` は CMake で `$<$<CONFIG:Debug,RelWithDebInfo>:DEBUG>` と定義する（CMake の Debug ビルドは `DEBUG` を定義しないため）
- 開発を助けるための機能は、すべて `#ifdef DEBUG` で囲み、Release ビルドには入れない
  - 対象：ImGui と rlImGui、当たり判定の表示、FPS とオブジェクト数の表示、無敵、ステージスキップ、ホットリロード、確保の回数を数える仕組み
- ImGui と rlImGui は、Debug と RelWithDebInfo でだけリンクする

## Quine の敵（[ADR 0002](decisions/0002-quine-enemy-text.md)）

- 敵の挙動関数は `// QUINE-BEGIN <敵ID>` と `// QUINE-END` で囲む
  - マーカーの行は範囲に含めない。範囲は1つの敵につき1つで、中に関数を複数書いてよい
  - 敵 ID は英小文字・数字・`_` で書く。`boss_` で始まる ID の敵がボス
- QUINE 範囲に難易度の数値（HP、速度、弾の数、角度など）を直接書かない。JSON から読む
  - 書いてよい数値は、10進数で値が 0、1、2、0.5 のものだけ。小数点と接尾辞 `f` は付けてよい（`2.0f`、`.5f` など）
  - 大文字の名前（英大文字・数字・`_` だけでできた識別子）は、raylib の `PI`、`DEG2RAD`、`RAD2DEG` だけ
  - 文字列と文字のリテラルを書かない
  - QUINE 範囲から呼ぶ範囲外の関数と変数にも、難易度の数値を書かない。JSON から読んだ値を渡す
- QUINE 範囲には ASCII の文字だけを使い、コメントを書かない。説明は `QUINE-BEGIN` の上に書く
- quine_pack は、QUINE 範囲の数値、大文字の名前、文字列と文字のリテラル、コメント、ASCII 以外の文字と、範囲とマスクの対応、マスクの形式と大きさを検査し、違反があればビルドエラーにする
- 敵の形はマスクファイルで決める。コードの長さに合わせてマスクを変えない

## 表示（[ADR 0008](decisions/0008-screen-scaling.md)）

- 画面の座標は 480×640 固定。表示するときは座標だけを拡大し、ウィンドウの実際の解像度で描く
  - フォントは拡大率に合わせた大きさで読み込み、`Camera2D` で拡大して描く
  - ウィンドウの大きさは起動時に決めて固定する
- 物として見えるもの（自機、敵、弾、UI、爆発などのエフェクト）は、すべて文字で描く。使う文字は ASCII だけ
  - 画面全体にかける効果（背景の塗りつぶし、フェード、フラッシュ）とデバッグ表示は、図形で描いてよい
- フォントは JetBrains Mono。大きさは 480×640 の座標で 12px

## 検査

原則のうち機械的に確かめられるものは、ビルドの中で確かめる。

| 原則 | 確かめる方法 |
| --- | --- |
| 例外を使わない | コンパイラ（例外を無効にしてビルドする） |
| 戻り値を確かめる | コンパイラ（`[[nodiscard]]` と、警告をエラーとして扱う設定） |
| プラットフォームを判定するマクロの場所と回数、使わない関数（ADR 0006 の表のうち、確かめ方が「スクリプト」の行）、入力・時間・乱数の関数を呼んでよい場所 | CMake のスクリプト。ビルドのたびに実行し、違反があればビルドを止める |
| 1ファイル500行 | 同じスクリプト。超えたファイルがあれば警告だけを出す |
| QUINE 範囲の制約、範囲とマスクの対応、マスクの形式と大きさ | quine_pack |
| 動的確保 | 確保の回数を数える仕組み |
| 命名、`update()` の中の `Draw*`、QUINE 範囲から呼ぶ範囲外の関数と変数の数値、nlohmann/json の `get<T>()` の前の型の確認 | レビュー |
